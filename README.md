# titanic classification
## 1. 프로젝트 개요 
Kaggle Titanic 데이터를 사용하여 승객의 생존 여부를 예측하는 이진 분류 프로젝트이다. 

핸즈온 머신러닝 2장에서 설명하는 머신러닝 프로젝트의 전체 과정을 직접 적용하는 것을 목표로 진행하였다.

### 진행 과정
1. 데이터 탐색
2. 테스트셋 분리
3. 데이터 시각화 및 EDA
4. 베이스라인 모델 학습
5. 피처 엔지니어링
6. 교차검증을 통한 모델 비교 및 후보모델 선정
7. GridSearchCV를 이용한 하이퍼파라미터 튜닝
8. 최종 모델 재학습
9. 제출

## 2. 데이터 분할 및 평가 전략
Kaggle에서 제공되는 데이터는 다음과 같습니다.

| 데이터 | 정답 포함 여부 | 용도 |
|---|---|---| 
| Kaggle `train.csv` | `Survived` 포함 | 모델 학습 및 로컬 평가 | 
| Kaggle `test.csv` | `Survived` 미포함 | 최종 제출 결과 생성 |

따라서 kaggle의 `test.csv`에는 정답이 없으므로 모델 개발 과정에서 성능 평가에 직접 사용할 수 없다.

Kaggle Public LB는 피처 엔지니어링과 하이퍼파라미터 탐색 과정에는 사용하지 않았다. 모델 개발이 끝난 뒤 최종 후보 모델의 외부 성능을 확인하기 위한 참고 지표로 사용하였다.

따라서 정답이 포함된 `train.csv`를 로컬 학습셋과 로컬 테스트셋으로 다시 분리하였다.

```text
###개발 과정에 사용되는 로컬 데이터 세트
data/processed/01/ 
├── train.csv 
└── test.csv

###캐글에서 제공한 원본 데이터셋
data/raw/ 
├── train.csv 
└── test.csv
```

### 2.1 로컬 학습셋과 테스트셋 분리

| 설정	           | 값                     |
|---------------|-----------------------|
| 로컬 학습셋	       | Kaggle train.csv의 80% |
| 로컬 테스트셋	      | Kaggle train.csv의 20% |
| 계층 분할 기준	     | Pclass                |
| random_state	 | 42                    |

* 이때 계층 분할 기준은 직관적으로 pclass가 가장 강하게 연관이 있을 것 같아 비율을 유지하려고 계층 분할을 했다.
* 하지만 이진 분류에서는 보통 타깃인 Survived를 기준으로 계층 분할을 한다고 하여 다음부터는 타깃의 비율을 우선적으로 고려해야겠다.


### 2.2 데이터 사용 흐름
```
Kaggle train.csv
│
├── 로컬 학습셋 80%
│   │
│   ├── 5-fold 교차검증
│   │   └── 피처 구성과 모델 비교
│   │
│   └── 10-fold GridSearchCV
│       └── 하이퍼파라미터 탐색
│
└── 로컬 테스트셋 20%
    └── 선택이 완료된 모델의 최종 로컬 성능 평가
```
모델과 하이퍼파라미터 선택이 모두 끝난 뒤에는 Kaggle train.csv 전체를 사용하여 최종 모델을 다시 학습하였다.

Kaggle Public LB 점수는 로컬 테스트 점수와 별개의 외부 평가 결과이다.

로컬 학습셋 내부의 교차검증 점수는 모델과 하이퍼파라미터를 선택하는 데 사용하였고, 
로컬 테스트셋은 선택이 끝난 모델의 최종 성능을 확인하는 데 사용하였다. 
이후 제출 단계에서는 Kaggle train.csv 전체로 모델을 다시 학습한 뒤 Kaggle test.csv를 예측하였다.

## 4. 피처 및 모델 실험

  * 각 실험 별 성능 측정은 로컬 학습 세트를 이용하여 k-fold점수로 평가

## 7. 회고
이번 프로젝트는 kaggle점수를 높게 받는 것보다 머신러닝 프로젝트의 전체 흐름을 직접 경험해보는데에 의의가 있었다.

피처를 추가하고, 가공하는 과정에서 해당 작업이 항상 성능 향상으로 이어지는 것은 아니었다. 같은 피처를 사용하더라도 전처리 방식에 따라 결과가 달라졌으며 모델에 따라 달라졌다. 이는 피처를 가공하는 과정에서 기존 정보가 단순화되거나 새로운 정보가 추가되고, 모델마다 이러한 피처를 활용하는 방식이 다르기 때문이라고 생각한다.

코드 작성 측면에서는 전처리 과정을 Pipeline과 ColumnTransformer 안에 포함시키면서, 교차검증 과정에서 각 fold의 학습 데이터만으로 전처리기가 학습되도록 구성하였다. 이를 통해 전처리와 모델 학습을 하나의 객체로 관리하는 방법과 데이터 누수를 방지하는 기본적인 구조를 익힐 수 있었다.

아쉬운 점은 프로젝트를 진행하면서 각 실험별 조건이 명확하게 고정되지 않고 체계적이지 않았다는 점이다. 평가 척도 또한 각 단계별로 여러가지를 섞어서 사용하고 표준편차까지 고려하지 않다보니 정확한 결과 해석이 어려웠다.

### 다음 프로젝트에서 고려할 점

- 실험 전에 데이터, 평가 지표, 교차검증 방법과 기본 모델 조건을 고정한다.
- 평균 교차검증 점수뿐만 아니라 fold별 점수와 표준편차도 함께 기록한다.
- 필요할 경우 반복 교차검증을 적용하여 평가 결과의 안정성을 확인한다.
- 피처 버전, 모델, 하이퍼파라미터와 평가 결과를 실험 단위로 함께 기록한다.
- 일부 모델만 고정하여 비교하지 않고, 여러 모델과 하이퍼파라미터 조합을 체계적으로 탐색한다.
- 공통 전처리를 재사용할 수 있도록 파이프라인 구성 코드를 개선한다.
